# Tazkiyane — permanent Android release signing foundation

This change prepares Tazkiyane `0.4.13+20` to use one permanent Android release
signing identity for every future GitHub Actions APK. It does not add app
features or alter the SQLite schema.

## Why this is necessary

Android accepts an ordinary in-place APK update only when the application ID
and signing identity remain compatible and the new version code is higher.
The Android application ID must stay:

`dev.tickoffreplacement.tickoff_replacement`

The current release APK was signed with an automatically generated Android
Debug certificate. Future CI builds must not create a fresh signing identity.
This workflow therefore fails closed when the permanent signing secrets are
missing, and verifies the final APK's SHA-256 certificate fingerprint.

## One-time setup — Flutter is not required on your PC

A JDK with `keytool` is required only to generate the private keystore. Flutter
and Android Studio are not required. Run these steps on the Windows computer
where the source project is extracted.

1. Apply this patch to the project.
2. Open PowerShell in the project root.
3. Run:

   ```powershell
   powershell -ExecutionPolicy Bypass -File .\tool\generate_android_keystore.ps1
   ```

4. When `keytool` prompts, choose a strong keystore password and store it in a
   password manager. At the key-password prompt, press Enter to reuse the same
   password. The alias generated by the script is `tazkiyane`.
5. The script creates two local files:
   - `tazkiyane-release.jks` — the private signing keystore.
   - `tazkiyane-release-keystore.base64.txt` — encoded keystore contents for a
     GitHub Actions secret.
6. In GitHub, open **Repository → Settings → Secrets and variables → Actions**
   and create these four **repository secrets**:

   | Secret name | Value |
   | --- | --- |
   | `ANDROID_KEYSTORE_BASE64` | Entire contents of `tazkiyane-release-keystore.base64.txt` |
   | `ANDROID_KEYSTORE_PASSWORD` | Keystore password entered above |
   | `ANDROID_KEY_ALIAS` | `tazkiyane` |
   | `ANDROID_KEY_PASSWORD` | Key password entered above (same password if Enter was pressed) |

7. Keep an encrypted offline backup of `tazkiyane-release.jks` and the two
   passwords. Losing the keystore means future APKs cannot use this signing
   identity. Never upload the `.jks` or Base64 file into the Git repository,
   an issue, a chat, or a workflow artifact.
8. Only after all four GitHub secrets are saved, commit and push the patch.

The workflow decodes the keystore into the ephemeral GitHub runner's temporary
folder, uses it to sign the release APK, and verifies the resulting APK
certificate. The private keystore is not included in the APK artifact.

## One-time installation transition

The currently installed `0.4.12+19` APK is signed with an Android Debug
certificate that differs from the new permanent release certificate. Android
will not accept the new key as a normal update to that installation.

Because the owner has explicitly accepted losing the old local data, the
one-time transition is:

1. Wait for the new `0.4.13+20` GitHub Actions workflow to pass all tests and
   signing verification, then download its APK artifact.
2. Uninstall the currently installed Tazkiyane app once.
3. Install the new `0.4.13+20` APK.
4. From that point forward, install newer APKs directly over the installed
   app. Do not uninstall the app for routine releases.

This initial uninstall removes the old app's private data. The first
permanently signed installation starts with an empty database, as accepted by
the owner.

## Future update rules

- Keep the application ID exactly `dev.tickoffreplacement.tickoff_replacement`.
- Keep using the same four GitHub secrets and never regenerate/replace the key.
- Increase the `+buildNumber` in `pubspec.yaml` for every APK distributed.
- Use versioned SQLite migrations for schema changes; do not delete or recreate
  the database during upgrades.
- Keep attachments under app-private persistent storage, as the current app
  already does.
- Do not uninstall the application when installing normal future releases.

An ordinary in-place Android update with the same application ID and signing
identity retains the app's private files, including the SQLite database and
local attachment directory. Database migrations must still preserve records
when the schema changes.
